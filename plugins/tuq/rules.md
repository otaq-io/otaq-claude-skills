# tuq: the rules of the `tuq/` folder

Every tuq skill (`tuq:product-spec`, `tuq:step-back`, `tuq:tech-spec`, `tuq:milestone-plan`) reads these rules (`tuq
rules` prints them) before it reads or writes `tuq/`. It is the one place these rules are written; the skills don't
repeat them.

The helper for everything mechanical is the `tuq` command, which the tuq plugin puts on the Bash tool's PATH:

```sh
tuq rules                 # prints these rules
tuq template decision     # prints a template: decision | readme | tech-spec | plan | orchestrator
tuq init                  # creates tuq/README.md (+ decisions/) when missing; prints the repo root. Never overwrites.
tuq next                  # prints the next free decision number: 008
tuq index                 # rebuilds the index table in tuq/README.md from the decision files
tuq clashes               # prints numbers used by more than one file; exit 1 if any
```

`tuq: command not found` means the tuq plugin isn't enabled in this session: stop and say so; never rebuild
its files by hand.

## Layout

- `tuq/` sits at the **repository root** (`git rev-parse --show-toplevel`; outside a git repository, the current
  directory, and say so). It is committed with the code.
- `tuq/README.md` explains the folder and holds the **decision index**, between the markers
  `<!-- tuq:index:start -->` and `<!-- tuq:index:end -->`. The index is generated by `tuq index` from
  the decision files: **never edit the rows by hand**; run `index` after every write. Text outside the markers is
  the repo's own and is never touched by the script.
- `tuq/decisions/` holds one file per product decision. Later tuq skills add their own subfolders.
- `tuq/tech-specs/<feature>.md` holds the tech spec of one feature: how it is built. One file per feature, updated
  in place on rework; `<feature>` is the same name as the feature's plan and prompt below.
- `tuq/plans/<feature>.md` holds the milestone plan of one feature: its pieces and what each waits for. `<feature>`
  is the same name as the feature's tech spec, `tuq/tech-specs/<feature>.md`.
- `tuq/prompts/<feature>-orchestrator.md` holds the orchestrator prompt for that plan: how the agent in charge
  runs the pieces.
- **First write in a repo with no `tuq/`:** run `tuq init`, then add a short pointer to `tuq/README.md`
  in the root `README.md` and `CLAUDE.md`, **only to those that exist** (create neither), for example:

  ```markdown
  ## Product decisions (tuq)

  Product decisions live in `tuq/decisions/`, indexed in `tuq/README.md`. Read the index before changing a
  feature's behaviour.
  ```

## Tech specs

- Start from `tuq template tech-spec`. The header is exactly these lines, nothing else:

  ```markdown
  - **Ticket:** SHOP-40
  - **Date:** 2026-11-05
  - **Decisions:** 008, 009
  ```

  `Ticket` is left out when there is none; `Date` is the day of the latest change; `Decisions` lists the product
  decisions it builds on, by number (`none` when there are none).

- The **diagram owns the dependencies**: who calls or imports whom is written once, as the arrows of its `text`
  diagram, never again in a table.
- No index: a tech spec is found by its feature name, or by its `Ticket` line. Everything else about it (the
  sections, the discussion, the come-back) is in the `tuq:tech-spec` skill.

## Plans and orchestrator prompts

- The **plan file owns the pieces**. The text between its markers `<!-- tuq:plan:start -->` and
  `<!-- tuq:plan:end -->` is the ticket's Plan word for word, ending in `## Pieces`: change the pieces there, never
  only in the ticket.
- The orchestrator prompt's **run order is generated** from the plan's waits, between `<!-- tuq:order:start -->`
  and `<!-- tuq:order:end -->`: never edit it by hand.
- The shape of both files is checked by `tuq-plan check <feature>`.
  Everything else about them (how pieces are cut, the commands, the come-back) is in the `tuq:milestone-plan` skill.
- No index: plans and prompts are found by their feature name.

## Numbering

- File name: `tuq/decisions/NNN-<slug>.md`. `NNN` is the number, zero-padded to three digits (`1000` after `999`);
  the slug is 2–5 lowercase words in kebab-case from the title (`reading-list-sharing`).
- A new decision takes `tuq next`: the highest number on the current branch plus one. Superseded files count,
  so **numbers are never reused**.
- Cite decisions by number: "Decision 008", or `008` in a header.

## The decision file

Start from `tuq template decision`. Keep it short and in this shape:

```markdown
# 008 · Reading lists can be shared by link

- **Date:** 2026-11-05
- **Ticket:** SHOP-40
- **Status:** Accepted
- **Supersedes:** 004
- **Related:** 002

## Summary

One or two sentences: what was decided. `index` puts this paragraph in the index.

## Decision

- What was agreed, written so someone who never saw the conversation understands it.

## Why

The reason, including the alternatives the user turned down when that matters.
```

- **Title line** `# NNN · <short title>` (the `·` is required: `index` reads it).
- **Header:** `Date` (today, `YYYY-MM-DD`); `Ticket` (the Otaq ticket key, left out when there is none); `Status`;
  `Supersedes` and `Related` only when they apply (leave the lines out otherwise).
- **Summary:** one paragraph, one or two sentences. **Decision:** bullets. **Why:** a short paragraph.
- No implementation in a product decision: what the user sees and can do, for whom, the data, the edge cases, what is
  out of scope. How it is built belongs to the tech spec.

## Statuses

| Status                    | Meaning                                                     | Counts in conflict checks |
| ------------------------- | ----------------------------------------------------------- | ------------------------- |
| `Accepted`                | in force                                                    | yes                       |
| `Partly superseded by NNN` | in force except what decision NNN changed (read both)      | yes                       |
| `Superseded by NNN`       | replaced by decision NNN; kept for the history              | no                        |

## When a decision is written, and how it changes

- One file per agreed point, written **right after it is agreed** (after the conflict check), not batched at the end.
  Then run `tuq index`.
- A decision written **in this session and not yet committed** may simply be edited when the user changes their mind:
  it never left the conversation. Run `index` after the edit.
- Anything **committed, or from an earlier session**, changes only through a **new decision that supersedes it**:
  the new file gets `- **Supersedes:** NNN`; in the old file **only its Status line changes**, to
  `Superseded by <new>` or `Partly superseded by <new>`. Its text is never rewritten or deleted.

## The conflict check

Run it as soon as a point is agreed, before its file is written:

1. Read the index, then open every `Accepted` or `Partly superseded` decision whose title or summary touches the same
   feature, data or rule as the new point.
2. A **conflict** is a new point that contradicts, narrows or undoes what an earlier decision says. One that only adds
   detail is not a conflict: list it under `Related`.
3. On a conflict, **don't save**. Ask the user, as the next question (asked the way the running skill asks), with
   every conflicting decision in one question:

   > Decision 008 conflicts with Decision 004: 004 says shared links never expire, 008 makes them expire after 30
   > days. Do you still want to proceed?

   | Option                       | Then                                                              |
   | ---------------------------- | ----------------------------------------------------------------- |
   | Proceed: 008 replaces 004    | write 008 with `Supersedes: 004`; 004's Status → `Superseded by 008` |
   | Proceed: only part of 004    | write 008 with `Supersedes: 004`; 004's Status → `Partly superseded by 008` |
   | Keep 004                     | 008 is not saved; the point goes back to the open list            |

4. Run `tuq index` after writing.

`tuq` doesn't judge conflicts: that takes reading.

## Renumbering after a clash

Two branches can take the same number. After a merge (or when the user asks), run `tuq clashes`. For each
number it reports:

1. **Keep** the file that was on the target branch first (`git log <target> --diff-filter=A --format=%H -- <file>`
   shows which branch added it); the others move.
2. Give each moving file the next free number (`tuq next`, in order) and rename it with `git mv`.
3. Rewrite its `# NNN ·` title, and every reference to its old number: the `Supersedes`, `Superseded by`,
   `Partly superseded by` and `Related` lines and any "Decision NNN" in prose, in **every file under `tuq/`**: the
   moved files, the decisions that cite them, and the `Decisions:` header lines (and prose) of tech specs, plans and
   prompts (`grep -rn "NNN" tuq/` finds them). Only references that mean the moved file change; the kept file
   keeps its number.
4. Run `tuq index` and `tuq clashes` (it must print nothing).
5. Show the user the renames (old → new) before committing in an Otaq stage; in a plain chat leave them uncommitted.
